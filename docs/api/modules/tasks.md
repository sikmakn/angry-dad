# Tasks и периоды

Создание `POST /tasks` проверяет конкретность и размер через AI, суточную квоту и параметры срока/повторения. При отказе AI задача не сохраняется. Каждый успешный запрос создаёт отдельную задачу, без ключа повторов. Связи описаны в [Task/Period](../data/task.md).

После создания клиент читает задачу и её периоды. Действия над сроком используют текущий `periodId`: `completion`, `extension`, `surrender`, `retry`. Остановка повторяющейся задачи передаётся поддержанным обновлением задачи; отдельный проектный `/tasks/{id}/stop` не является фактическим маршрутом.

Успех и штраф фиксируются с переходом периода и изменением уважения в транзакции. На границе `deadline <= now` закрытие, продление, сдача и ответы check-in отклоняются с 409, даже если статус в БД ещё `active`. Сам отказ не применяет провал: это делает deadline sweeper по исходному времени срока. Он также перечитывает срок, чтобы устаревший кандидат не провалил уже продлённый/восстановленный период.

Deadline lifecycle работает отдельно от расписания уведомлений: отказ отправки не продлевает задачу. Worker открывает следующие периоды повторяющихся задач. Просрочки обходятся общими пачками до 200 Period по `_id` с продолжением на следующих тиках; это размер работы по всей базе, не лимит задач пользователя. После конца обхода курсор сбрасывается, после рестарта круг начинается заново.

Удаление скрывает задачу и закрывает ещё активные периоды без новой награды/штрафа; счётчик рейтинга корректируется для удалённых выполнений. Отдельные крайние гонки не объявляются полностью покрытыми: [результаты тестов](../../testing/mvp-backend-results.md).
