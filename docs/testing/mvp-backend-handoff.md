# Передача тестеру бэкенда MVP

Ветка: `feat/mvp-api`. Дата заметки: 2026-10-24.

Текущий итог: семь замечаний ревью исправлены и повторно проверены; постоянный набор выполнил 176 тестов в 15 suites без падений и пропусков. Подтверждённый охват, ограничения и состояние общего шлюза — в [результатах](mvp-backend-results.md). Ниже сохранена исходная матрица передачи; её пункты не следует автоматически считать полностью покрытыми одним успешным набором.

## Порядок работы, согласованный с Никитой

Пользователь разрешил независимое ревью, затем тестера после чистого результата; после исправления семи замечаний этот переход выполнен. Сценарии и постоянные тесты пишет test-writer; родитель не создаёт дополнительных временных сценарных скриптов. Из-за ограничения sandbox роли родитель выполняет её штатный Docker-прогон и передаёт вывод. Пользователь также разрешил простые ошибки исправлять самостоятельно, важные/неоднозначные обсуждать, а после успешных проверок — коммит и локальное слияние main. Обязательный шлюз `npm run check` сохраняется; вопрос стыковки фронта передан оркестратору по указанию пользователя.

До этого решения родитель уже выполнил временные автоматические проверки на изолированной MongoDB с подставными внешними клиентами. Ниже сохранено, что именно проверялось, чтобы тестер мог использовать материал. Это не постоянный набор тестов, не основание пропускать независимую проверку и не результат проверки реальных интеграций.

## Изменённое поведение

- Независимое ревью выявило семь дефектов; [исходный отчёт и повторные проверки](../architecture/mvp/backend-review.md) сохранены. Исправлены оба курсора, отправка готовой реакции callback, обход всех диалогов пачками, продвижение обработки дедлайнов, проверка срока в запросах и распознавание глобального префикса активности. Это исправления известных требований, без новых HTTP-маршрутов. Обе группы (4–7 и 1–3) повторно проверены ревьюером без замечаний. Сценарии ниже переданы тестеру; результаты его прогонов будут записаны отдельно.

- По D10 генерация перефразов и смена статуса обращения публикуют локальные асинхронные события журнала после записи данных, без новых транзакций. Ошибка подписчика не отменяет действие; редкая потеря события допустима. Фильтр журнала и Swagger enum дополнены. Обычные npm-команды API start/dev/debug экспортируют контракт перед запуском, отдельные watch-rebuild этого не делают.

- По D9 источником фактического HTTP-контракта стали NestJS controllers/DTO/Swagger metadata. `generate:openapi` пишет только YAML/JSON в docs, `check:openapi` сверяет их с кодом. Фронтенд самостоятельно пересобирает типы; его файлы в этой правке не менялись. Добавлены повторные 200/409 роли; ключ с другим пакетом/сообщением теперь 409 idempotency_key_reused. Подробности — [контракт](../architecture/mvp/api-contract.md).

- Первые даты/дневная статистика и `task_created` переведены на локальные асинхронные события по [D8](../architecture/mvp/analytics.md#доставка-событий-по-d8). `TasksService` публикует событие после коммита; guard только авторизует. HTTP-активность наблюдает interceptor, users синхронно обновляет операционный `lastActivityAt`, затем публикует событие статистики. Редкая потеря статистики допустима; Redis/outbox/Change Streams нет. Финансовые снимки и остальные события аналитики сохранены.

- Уведомления переведены на [единое адаптивное расписание пользователя](../architecture/mvp/task-notifications.md): одно состояние и один pending, минимум 3 минуты, предел 6 автоматических сообщений за скользящий час, короткая серия и пауза. Обязательные минимумы каждой задачи отменены. Старые проверки независимых расписаний ниже описывают прежний код и не являются приёмкой нового механизма.
- У создания задачи убран `Idempotency-Key`: каждый успешный вызов создаёт отдельную задачу. Финансовые ключи повторов сохранены.
- Входящие обновления Telegram учитываются в `TelegramUpdateReceipt` по `botId:updateId`, с арендой и продлением. Завершённые записи имеют TTL 48 часов. Для `/paysupport` источник обновления определяет одно обращение даже после сбоя отправки подтверждения.
- Повтор создания счёта с ключом использует прежние payload и снимок пакета. Получение ссылки защищено арендой с токеном владельца. Истечение срока ключа удаляет только ключ, сохраняя финансовую историю.
- Идентификатор pre-checkout закрепляется до внешнего ответа; повтор того же query допустим, другой query на закреплённом счёте отклоняется. Одобрение не означает оплату.
- Хук оплаты, сверка истории и восстановление legacy `paid` используют единое транзакционное зачисление. Условное изменение платежа предшествует grant; статус, партия, операция и purchase analytics фиксируются вместе.
- Worker при запуске и раз в минуту сверяет ожидающие платежи старше 5 минут. История читается порциями с продолжением, затем отдельным проходом проверяются возвраты. Свежие платежи ждут хук; отсутствие операции оставляет ожидание.
- Исключения оплаты сохраняются в `PaymentIncident`, без второго начисления и новых автоматических возвратов. Продолжение просмотра истории хранится в памяти и после рестарта начинается заново.

## Новые сценарии единого планировщика — ещё не выполнялись

1. Одно сохранённое время и не больше одного pending на пользователя при нескольких worker, конкурентных событиях, истечении аренд и рестарте. Обычные HTTP-чтения не меняют случайную дату.
2. Общий минимум 3 минуты, скользящий предел 6 сообщений/час, множество срочных задач и насыщение усиления. Недавние unknown должны учитываться даже при 200+ старых успешных записях; явные 4xx не считаются принятыми отправками.
3. Обычный режим, застой, короткая серия, побеждённость и пауза. Не должно возникать постоянного периода 3 минуты при большом количестве задач.
4. Ротация многих активных задач: давние основные упоминания не теряются из-за ограничения истории; вторичное упоминание не заменяет основную проверку. Срочные поводы учитываются без постоянного вытеснения остальных задач.
5. Основная задача однозначно названа; максимум одно вторичное упоминание без списка и выдуманного отрицательного ответа. Все кнопки, закрытие и штраф относятся к основной задаче.
6. Создание/закрытие/удаление/остановка/перенос/retry, новый период, смена роли/часового пояса/тихих часов во время ожидания, подготовки и внешнего send. Старый известный успех не стирает pending и дату новой ревизии.
7. Закрытие последней задачи, новая задача после idle, будущий `moodFrom`, переход через тихие часы, блокировка и разблокировка. Нет догоняющей пачки после простоя; legacy очередь не работает одновременно с новой.
8. Исходный неответ и дополнительные проверки серии дают не больше одного штрафа; после ответа partial/not_started и молчания на серию допускается первый штраф. Завершённое состояние серии может уже отсутствовать — устойчивый origin в outbox сохраняет общий ключ. Суточный cap3 остаётся.
9. Серия завершилась двумя отправками или истекла без доставки; затем пауза. Новые отрицательные ответы в активной серии/паузе не создают бесконечное пополнение серии.
10. Черновик недоступен через feed get/list, карточку задачи, ответы, оценку, battle reply и sharing. Неподтверждённая отправка не запускает 15 минут и не штрафует пользователя.
11. Восстановление аренды до внешней отправки пересоздаёт заготовку: подстановки времени до дедлайна и контекст не остаются от старой попытки.
12. Пустой пул фраз, 403/429/timeout, сбой базы до/после внешнего send, поздний успех после истечения аренды. Нет ложного успеха, немедленного слепого повтора и повторного расхода серии/учёта факта.
13. Один fail-повод на конкретный провал; отмена после retry и новый повод при новом провале. Устаревшие поводы/закрытые задачи не порождают проверки.
14. Удаление аккаунта одновременно с bootstrap/планированием/отправкой очищает state и нефинансовую историю; удалённый пользователь не получает новые обращения.
15. Оценить стоимость выборки последних основных упоминаний за полную историю активных кандидатов. Повторно проверить подключение Nest-модулей и HTTP-пути, которые не запускались при реализации.

Источник поведения и пороги: `docs/architecture/mvp/task-notifications.md`; исходники: `apps/api/src/modules/task-notifications/` и delivery. Эти пункты переданы как материал тестеру; статический шлюз не подтверждает их прохождение.

## Новые сценарии аналитики — ещё не выполнялись

Реализация и определения — [аналитика по D7](../architecture/mvp/analytics.md). Родитель и backend-dev запускали только статический шлюз. Следующие пункты предназначены будущему тестеру, не являются результатами прогонов:

1. Первый личный `/start`, прямой `GET /me`, повторный запуск и пользовательская мутация без предварительного getMe. Одно первое время; polling обычных GET, доставка и платёжные хуки не создают посещений. Фронтенд не должен опрашивать `/me` в фоне.
2. Личное текстовое сообщение и разрешённая кнопка считаются активностью. Чужой/групповой callback, pre-checkout, successful_payment, my_chat_member и действия владельца над другим пользователем не создают его активность.
3. Одновременные первые события и создание двух задач: уникальность статистики и минимальные исходные времена при перестановке обработчиков. `task.created` публикуется только после успешного коммита; ошибка ИИ/rollback и повтор callback Mongo-транзакции не публикуют промежуточные события. Статистическая транзакция подписчика отделена от транзакции задачи. Асинхронную проекцию проверять после завершения подписчика.
4. Конкурентное удаление аккаунта и запись активности/задачи: обе коллекции очищаются, запись не воскрешается. Новый аккаунт начинает новую историю; неизвестное прошлое не выдумывается.
5. UTC-полуночь, переходы месяца/года, D7 на нужном дне, незавершившийся D7, `to` в прошлом/будущем, пустая и нулевая зрелая когорта. Для активных выбираются целые UTC-дни, в том числе при неполных граничных сутках; внутренние визиты не теряются из-за проверки только первого/последнего времени дня.
6. Медиана нечётного/чётного набора, округление секунд только после вычисления, без первой задачи/без известного старта, задача после `to`, отрицательный интервал старой неконсистентной записи.
7. Блокировка известного пользователя сохраняет userId и событие в одной транзакции. Дубли/разблокировка не дают новый bot_blocked; неизвестный чат не создаёт User. Доля блокировок среди активных находится в [0,1]. Onboarding и событие также атомарны.
8. Доля ответов по реально отправленным проверкам: черновик/нет Telegram id, вчерашняя отправка и сегодняшний ответ, поздний принятый ответ, ответ после `to`, отсутствие отправок. Окно штрафа 15 минут не ограничивает эту метрику.
9. Значения env, явные пустые/отрицательные/NaN/бесконечные тарифы, SMART/FAST и совместимость прежних model overrides. Разные входной/выходной тарифы, сохранение снимков после смены конфигурации.
10. Отдельные AiCall для повторов, точная привязка invalid по id, отказ с usage, известный ноль, неизвестная стоимость, pending после сбоя учёта, timeout без поздней сверки. Подставные вызовы не дают ложные 0% экономики.
11. Снимок курса нового счёта, повтор/подтверждение после изменения курса, старый счёт без курса. Публичный packageSnapshot не изменён; платёжная идемпотентность сохранена.
12. Цена единицы из партии, платные и ручные удары, consumed/reserved/refunded, повторы и неудачные платные попытки, нулевая выручка и исторические записи без снимка. Одна когорта резервирований для расходов и выручки; удаление Turn не теряет сохранённое экономическое состояние.
13. Фоновое сжатие учитывается у последнего хода сжимаемого фрагмента, в том числе после конца периода; старые summaries без turnId не приписываются произвольно. Доступ владельца к метрикам; стоимость пакетных выборок на большой когорте без N+1.
14. Ошибка/задержка подписчика и синхронная ошибка публикации не меняют успешный результат задачи и не дают unhandled rejection. В логах только тип события и класс ошибки, без payload/текста/Telegram-профиля. Потеря между commit и обработкой допустима; восстановление после перезапуска не ожидается.
15. EventsModule/подписчики зарегистрированы один раз на контекст API и worker. Событие обрабатывается в процессе-источнике, при нескольких API не требуется межпроцессная доставка. Это сценарии будущего тестера, при реализации Nest-контексты не запускались.
16. User.lastActivityAt меняется синхронно при допустимой активности даже при сбое статистики, использует `$max`. Guard не пишет статистику; interceptor сохраняет прежние HTTP-фильтры, бот — проверки личного чата/принадлежности кнопки. Поздние события удалённого/удаляемого пользователя не создают статистику или identified task_created повторно. Финансовые события и состояния остаются в прежних транзакциях.

## Новые сценарии фактического HTTP-контракта — ещё не выполнялись

Офлайн-экспорт и статическая сверка выполнены при реализации; следующие HTTP/поведенческие проверки оставлены будущему тестеру:

1. Успешное первое создание счёта, ручной операции, цитаты возвращает 201; идентичный повтор с ключом — 200 с прежним телом и без повторного эффекта. Проверить фактический Location, отсутствие повторного списания/начисления и ключи длины 8–64.
2. Один ключ с другим пакетом, feedMessageId или параметрами ручных ударов даёт 409 idempotency_key_reused. Для хода боя сохраняются pending409/failed502/successful200; новая попытка failed использует новый ключ. Создание задачи ключом не защищено.
3. Роль, отличная от текущей, даёт 409 role_mismatch на обоих GET боя, цитате и battle-карточке шеринга. Права владельца и чужие ресурсы сохраняют 403/404.
4. Все ошибки имеют application/problem+json и Problem.required; дополнительные reply/periodStatus/errors соответствуют конкретной ошибке. 204 без тела, nullable и необязательные поля не перепутаны, integer/enum/параметры/границы совпадают с runtime-валидацией.
5. Authorization передаётся как tma initData, не Bearer. Вебхук требует только свой секрет; завершённый/повторный update даёт 200, временный сбой 503, некорректный update_id 400. Уведомления используют реальную ленту/ответы без нового публичного endpoint внутреннего расписания.
6. Изменение Swagger-метаданных делает check:openapi красным без перезаписи YAML/JSON; повторный экспорт восстанавливает соответствие. Проверить CI без `.env`, MongoDB и секретов: генерация не должна запускать провайдеры, worker, seed или слушающий HTTP-сервер. Файлы фронтенда не обновляются этой командой.
7. После самостоятельной пересборки типов фронтендом общий npm run check должен снова проходить. Его прежняя проверка check:api сохранена; отсутствие свежих типов не обходится ослаблением шлюза.

## Новые сценарии журнала и экспорта перед запуском — ещё не выполнялись

Родитель и backend-dev выполняли только статические проверки и отдельный офлайн-экспорт. Приложение и npm-команды start не запускались. Материал будущему тестеру:

Фактическая проверка D10: API typecheck, lint, экспорт и `check:openapi` прошли. Полный `npm run check` остановился на прежнем `check:api`: типы фронтенда устарели. По указанию пользователя они не пересобирались; сверка файла до/после подтвердила отсутствие изменений. Шлюз не ослаблялся.

1. Успешная генерация N вариантов публикует одно `phrase.paraphrases.generated`; журнал `paraphrase_generate` содержит ID исходной фразы, точные `generatedIds/count` и время события. Пустая пачка сохраняет прежнее допустимое поведение с count=0. Одобрение варианта остаётся отдельным review.
2. Ошибка AI/БД до успешного сохранения пачки не публикует событие успеха. Сохранение нескольких Phrase осталось без общей транзакции: при частичной ошибке возможны уже сохранённые варианты без события о завершении всей пачки. Не ожидать отката пачки ради журнала.
3. `open → resolved` и обратный переход дают правильные `from/to` из прежнего документа атомарного `findOneAndUpdate`. Повтор текущего статуса не публикует событие, отсутствующий ID даёт 404. Конкурентные одинаковые запросы создают одно событие на реальный переход; различные изменения сохраняют фактический предыдущий статус.
4. Обращение без userId или с отсутствующим User журналируется со снимком Telegram ID самого обращения. Время берётся из события, не из момента позднего выполнения подписчика. Тексты фраз/обращения в payload/details и логи ошибок не попадают.
5. Сбой асинхронной записи и синхронная ошибка dispatch не делают успешно выполненное действие ошибкой HTTP и не дают unhandled rejection. Потеря между действием и обработкой при остановке процесса допустима; восстановления и гарантии постоянной очереди нет.
6. Обработчики событий зарегистрированы один раз в API/worker. GET owner/journal принимает оба новых action в фильтре и отдаёт прежнюю структуру; обычный пользователь по-прежнему не имеет доступа.
7. `npm start -w api`, `npm run start:dev -w api`, `npm run start:debug -w api` из корня и соответствующие команды из apps/api сначала генерируют оба OpenAPI-файла. При ошибке экспорта запуск не продолжается. Нет рекурсии build/экспорта, файлов фронтенда команда не меняет; отдельный watch-rebuild повторно экспорт не запускает. Production и worker работают без этого шага.

## Регрессии по семи замечаниям ревью — ещё не выполнялись

Номера относятся к исходному отчёту. Размеры 200 периодов и 100 диалогов — общие пачки по всей базе пользователей, не ограничения на одного пользователя. Материал будущему тестеру:

1. **Пачка дедлайнов:** более 200 просроченных `active` Period удалённых/отсутствующих задач у разных пользователей, затем живые просроченные задачи. За конечное число тиков обход доходит до живых задач; пропуски и короткие/пустые пачки не закрепляют курсор. Обход после конца/рестарта начинается сначала.
2. **Удаление задачи:** ещё активные периоды закрываются без нового штрафа, fail-уведомления и награды. Удаление и закрытие фиксируются существующей транзакцией; последующий sweeper не применяет штраф к удалённой задаче. Существующее изменение закрытого счётчика при удалении завершённых задач сохраняется.
3. **Граница срока:** `deadline=now−1мс`, `deadline=now`, `deadline=now+1мс`. Просроченные done/extend/surrender и check-in done/partial/not_started отклоняются с 409 и не дают награду, перенос или серию. Будущий срок остаётся допустимым при выполнении остальных условий. Сам отказ не фиксирует провал: его применяет sweeper по времени исходного дедлайна, со штрафом один раз.
4. **Устаревшая выборка:** sweeper выбрал прежний deadline, затем период был провален и восстановлен retry с будущим сроком. Старое действие deadline перечитывает срок и не проваливает восстановленный период. Проверить также допустимый перенос между выборкой и действием; нет преждевременного/повторного штрафа.
5. **Префикс активности:** одинаково проверить `/me` и `/api/me`, PATCH me, пользовательские мутации. Opening обновляет первое время/дневную статистику и операционный lastActivityAt. DELETE me, owner-маршруты с обоими префиксами и обычные GET/polling посещений не создают. Асинхронной статистике дать обработать событие.
6. **Курсор обращения:** ID `telegram:123:456`, `limit=1`, переходы по реально возвращаемым nextCursor. Все обращения доступны без 400/пропусков/повторов. Некорректные и чрезмерно длинные декодированные курсоры по-прежнему отклоняются.
7. **Курсор фраз:** sort=-shows и sort=avg, равные значения сортировки, seed ID с `_` и обычные ID. Маленькими страницами получить каждую фразу один раз, полный ID сохраняется после первого разделителя.
8. **Callback проверки:** «Частично» и «Не начинал» отправляют точный готовый непустой result.reply и подтверждают callback; null не отправляется. Повтор входящего Telegram update не повторяет бизнес-переход/ответ. Закрытый/просроченный период не даёт успешную реакцию. Telegram только подставной.
9. **Общий обход диалогов:** у более 100 разных пользователей первые 100 диалогов короткие/уже сжаты, последующие требуют summary. Следующие тики доходят до хвоста; пустая пачка возвращает обход к началу. Активный ход и единичная ошибка AI не блокируют остальных навсегда. Сохраняются порог >20, последние 8 сообщений, CAS summaryUpTo и привязка стоимости к последнему turnId сжимаемой части. Курсор обхода хранится в памяти и после рестарта начинает круг заново.

Новая реализация `task-notifications` сценарно **не проверялась**: после решения пользователя запускался только `npm run check`. Дальнейший список фактических прошлых прогонов относится к состоянию до этой переработки.

### Платежи — 14 групп

Все перечисленные группы прошли на момент этой заметки:

1. Повтор получения ссылки после ошибки: прежний payload и снимок, проверка несовпадающего пакета до получения URL, продолжение после отключения/изменения пакета.
2. Конкурентное создание счёта с одним ключом: одна запись, корректный повтор или допустимый 503, без ошибки дублирующего индекса наружу.
3. Потерянный ответ pre-checkout: закрепление сохраняется, тот же query повторяется, другой отклоняется; раннего начисления нет.
4. Шестнадцать одновременных подтверждений через разные экземпляры сервиса: одна партия, одна операция покупки, одно событие purchase.
5. Искусственная ошибка после grant внутри транзакции: полный откат и одно начисление после повтора новым экземпляром сервиса.
6. Конкурентное восстановление прежней записи `paid` через тот же путь зачисления.
7. История из трёх страниц, одновременные хук и сверка, возврат на странице до исходной оплаты, отсутствие payload, отсутствие оплаты, исключение свежих платежей. Поздний хук найденной возвращённой оплаты не начисляет удары.
8. Продолжение ограниченного прохода по истории больше чем из 1000 операций, без потери старой оплаты.
9. Истечение аренды ссылки и замена владельца: запоздалый ответ старого владельца не перезаписывает новую ссылку.
10. Повторное использование истёкшего ключа не удаляет прежний платёж и начисление.
11. Отличающийся второй charge и несовпадающая сумма сохраняются как исключения без дополнительных ударов и автоматического возврата.
12. Подтверждение при удалении пользователя сохраняет факт оплаты, не выдавая удары.
13. Преобразование ответа истории Telegram, ограничение страницы 100 операциями, отсутствие сети в тестовом режиме клиента.
14. Сверка при запуске worker работает в фоне, не пересекается сама с собой, не задерживает обычные задания; остановка очищает таймеры и ожидает начатую работу.

Временный скрипт: `/tmp/angry-dad-payments-smoke.cjs`. Он вызывал сервисы напрямую и использовал заглушку Telegram; HTTP-маршруты и реальные оплаты не проверял.
