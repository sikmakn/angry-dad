# Решения и вопросы · [← сводка](00-overview.md)

## Предположения архитектора
Всё, что взято не из ТЗ, а придумано при проектировании. Статус: не подтверждено.

- <a id="a1"></a>**A1.** Одна кодовая база `apps/api`, два процесса из одной сборки: `api` (HTTP Mini App и вебхук бота) и `worker` (планировщик, отправка, восстановление ходов, дозачисление платежей, сжатие диалогов). Воркер масштабируется отдельно и не держит HTTP · влияет на: pressure, delivery, battle, payments
- <a id="a2"></a>**A2.** Расписание и очередь отправки лежат в MongoDB (`OutboxMessage` с арендой записи через атомарное обновление), без Redis. При 10 000 активных в сутки это порядка сотен тысяч сообщений в сутки, единицы в секунду · влияет на: pressure, delivery
- <a id="a3"></a>**A3.** MongoDB запускается как replica set (в разработке одноузловой): транзакции нужны для хода боя, платежа и закрытия задачи с уважением · влияет на: инфраструктура scaffold
- <a id="a4"></a>**A4.** Разовая задача хранится как `Task` с одним `Period`. Статусы, срок, продление, «Сделаю за час», настроение и проверки живут в `Period` для обоих видов задач, поэтому планировщик и жизненный цикл одни · влияет на: tasks, pressure
- <a id="a5"></a>**A5.** Часовой пояс хранится IANA-зоной с устройства (`Europe/Minsk`), чтобы учитывать переход на летнее время; Mini App показывает его смещением. Без данных с устройства — `Europe/Moscow` (UTC+3, A-3 ТЗ) · влияет на: User, все суточные правила
- <a id="a6"></a>**A6.** Побеждённость хранится значением и моментом записи; откат 25 в сутки считается при чтении, фоновой задачи нет · влияет на: battle, phrases, pressure
- <a id="a7"></a>**A7.** Фраза выбирается и подставляется в момент отправки, а не при планировании: уровень по настроению и побеждённость берутся на момент отправки (R-72) · влияет на: delivery, phrases
- <a id="a8"></a>**A8.** Mini App подтверждает пользователя подписанными данными запуска Telegram (`initData`) в каждом запросе; своих сессий и токенов нет. Кнопки бота проверяются по `from.id` нажавшего (пересланная проверка, UC-36) · влияет на: users, bot
- <a id="a9"></a>**A9.** Бот работает на grammY в режиме вебхука внутри процесса `api` · влияет на: bot
- <a id="a10"></a>**A10.** Для рейтинга в `User` хранятся число закрытых задач и момент, когда оно достигнуто; место считается запросом по индексу · влияет на: leaderboard, tasks
- <a id="a11"></a>**A11.** Сжатие диалога идёт фоном в воркере после хода; актёр берёт последнее готовое изложение и все реплики после него, поэтому ход не ждёт сжатия · влияет на: battle
- <a id="a12"></a>**A12.** Коэффициенты боя, суточный лимит ИИ, список имён `{other}` и пороги бандита лежат в `GameSettings` и меняются без выпуска версии; правка пишется в журнал владельца · влияет на: analytics, battle, phrases
- <a id="a13"></a>**A13.** Удаление аккаунта физически стирает данные пользователя; остаются платежи и операции ударов (с Telegram ID для владельца), счётчики фраз и `DeletedUser` с хешем Telegram ID для R-8 · влияет на: users, strikes, payments

## Вопросы

### Q1
**Суть:** где живут функции владельца (F-16 оставляет выбор архитектору).
**Варианты:** 1) раздел «Владелец» в той же Mini App, виден только Telegram ID владельца; 2) команды бота.
**Рекомендация:** 1. Списки фраз, отчёт наполнения и метрики в чате читать неудобно, а доступ проверяется тем же входом.
**Влияет на:** owner-контроллеры всех модулей, apps/web

### Q2
**Суть:** чем проверять конкретность и размер задачи (D11).
**Варианты:** 1) дешёвая внешняя модель через тот же шлюз ИИ; 2) своя модель на сервере.
**Рекомендация:** 1. Ответ за 3 секунды и 24 из 30 по размеру даёт любая мелкая модель; своя требует GPU или медленна на CPU. Шлюз оставляет возможность подключить свою позже.
**Влияет на:** ai, tasks, инфраструктура

### Q3
**Суть:** на чём очередь расписания и отправки.
**Варианты:** 1) MongoDB (коллекция с арендой записи); 2) Redis и BullMQ.
**Рекомендация:** 1. Нагрузка небольшая, одна база проще в эксплуатации и транзакциях; Redis можно добавить, если упрёмся.
**Влияет на:** pressure, delivery, инфраструктура

### Q4
**Суть:** карточка шеринга — изображение или текст (Q-6 ТЗ).
**Варианты:** 1) изображение, рисуется на сервере из шаблона без ИИ; 2) текстовое сообщение со ссылкой.
**Рекомендация:** 1. Генерация шаблоном (SVG в PNG) почти бесплатна, бюджет ИИ не тратит.
**Влияет на:** sharing

### Q5
**Суть:** где запускать сервис и базу.
**Варианты:** 1) один сервер с Docker (api, worker, web), MongoDB Atlas; 2) один сервер, MongoDB там же в контейнере; 3) решить на шаге scaffold.
**Рекомендация:** 1. Atlas сразу даёт replica set и бэкапы; для N-8 (99%) одного сервера хватает.
**Влияет на:** scaffold, деплой

### Открытые вопросы ТЗ, архитектуру не блокируют
- **Q-1 ТЗ** (вывод Stars): платежи за шлюзом с тестовой средой Telegram; если Stars нельзя, меняется только модуль payments.
- **Q-2 ТЗ** (провайдер ИИ): шлюз с заменяемым провайдером и подставным провайдером для тестов; доля отказов и токены пишутся в `AiCall` для замера на 50 жёстких ходах.

## Принято
- **D10.** Генерация пачки перефразов и реальная смена статуса обращения дополняют журнал владельца через локальные асинхронные события. `paraphrase_generate` содержит исходную фразу, количество и ID сохранённых вариантов; `support_ticket_status_changed` — обращение и фактические `from/to`. Повтор текущего статуса события не создаёт. Ошибка журнала не отменяет действие; редкая потеря записи при падении процесса допустима. Новые транзакции, Redis и постоянная очередь для журнала не нужны; прежние денежные операции сохраняют свою атомарность. Обычные npm-команды API `start`, `start:dev`, `start:debug` автоматически запускают существующий Swagger-экспорт перед стартом; отдельные watch-rebuild, production и worker его не запускают. YAML/JSON вручную не редактируются, файлы фронтенда не меняются. Ревью и сценарные тесты остаются будущему этапу. [Журнал](entities/owner-action.md), [экспорт контракта](api-contract.md) · 2026-10-24 · Никита
- **D9.** Прежний ручной контракт считается наброском; фактический контракт строится из NestJS controllers/DTO и `@nestjs/swagger`. Экспорт сохраняет `docs/openapi.yaml` и `docs/openapi.json` на прежних местах; фронтенд самостоятельно пересобирает свои типы. `npm run generate:openapi` обновляет только контракт, `check:openapi` проверяет воспроизводимость без записи. Экспорт работает в preview без `.env`, MongoDB, HTTP-listen и внешних клиентов. Добавлены недостающие повторные 200/конфликты роли 409; повтор ключа с другим пакетом/сообщением унифицирован на 409 `idempotency_key_reused`. Срок ключа цитаты описан отдельно от финансовых 24 часов. Новые HTTP-маршруты для внутреннего планировщика не создаются; все реальные маршруты ленты/ответов сканируются автоматически. Это решение заменяет прежнюю заморозку YAML для текущего MVP; ревью и сценарные тесты пока не запускать. [Фактический контракт](api-contract.md) · 2026-10-24 · Никита
- **D8.** Для первых событий и дневной статистики допустима редкая потеря данных. Прямые вызовы `UserStatisticsService` из `TasksService`, auth guard и обработчиков бота заменены событиями `@nestjs/event-emitter` внутри процесса. `task.created` публикуется строго после коммита; подписчик асинхронно обновляет статистику и `task_created` AnalyticsEvent в своей транзакции, логирует ошибки без влияния на основной запрос. Guard проверяет только вход; HTTP-активность наблюдает interceptor. Операционный `User.lastActivityAt` остаётся синхронной ответственностью users, затем публикуется событие для статистики. Redis, постоянная очередь, outbox, Change Streams и восстановление потерянных событий не нужны. Поздние события не воскрешают удалённый аккаунт. Финансовые транзакции/снимки и остальные события аналитики сохраняются. Это уточнение заменяет прежнюю атомарность первой задачи и её статистики по D7. Подробности: [доставка событий](analytics.md#доставка-событий-по-d8) · 2026-10-24 · Никита
- **D7.** Добавлены отдельные `UserStatistics` и `UserActivityDay` для первого старта, первой сохранённой задачи и активности по UTC-дням. Начало — первый `/start` либо открытие Mini App; повтор не сбрасывает время. D7 учитывает завершившийся седьмой календарный день. Автоматические уведомления активностью не считаются; статистика удаляется с аккаунтом. Денежная единица — USD, Stars оцениваются по настраиваемым `$0.013/Star`, без налогов и расчёта вывода. Временные модельные ориентиры — Sonnet 4.6 и Haiku 4.5, тарифы входных/выходных токенов в `.env`. Неизвестная стоимость ИИ не заменяется нулём; курс и тарифы сохраняются снимками. Экономика сравнивает расходы платных попыток со стоимостью израсходованных платных ударов. Настоящий ИИ, ревью и сценарные тесты отложены. Формулы и границы: [аналитика](analytics.md) · 2026-10-24 · Никита
- **D6.** Одобрено единое адаптивное расписание обращений персонажа к пользователю вместо независимых расписаний каждой задачи. Один следующий момент, общий интервал не меньше трёх минут, ограничение плотности и коротких серий, выбор основной задачи по срочности/застою/давности упоминания, иногда вторая задача в тексте. Кнопки относятся к основной задаче. Старые обязательные минимумы проверок каждой задачи отменяются; фиксированные поводы учитывает общий планировщик. Состояние и история — в MongoDB, выполнение существующим worker без Redis/BullMQ и настоящего ИИ. Подробности и приоритет над прежними требованиями: [единое расписание](task-notifications.md) · 2026-10-24 · Никита
- **D1.** Набросок одобрен; Q1–Q5 приняты по рекомендациям: функции владельца в Mini App, лёгкая модель через шлюз ИИ, очередь в MongoDB, карточка-изображение, Docker и MongoDB Atlas · 2026-10-23 · Никита
- **D2.** Модуль `wallet` переименован в `strikes` (название не понравилось) · 2026-10-23 · Никита
- **D3.** Создание задач упрощено: `POST /tasks` создаёт отдельную задачу при каждом успешном вызове, ключ повтора и хранение прежнего результата для этой операции убраны. Защита платежей и операций с ударами от повторного выполнения сохраняется. Предложение K-6 из `contract-review.md` для задач отменено этим решением · 2026-10-23 · Никита
- **D4.** Учёт входящих событий Telegram хранится в MongoDB (`TelegramUpdateReceipt`), ключ — `botId:updateId`. Завершённые повторы подтверждаются без повторного запуска обработчика; незавершённая обработка защищена атомарным захватом с арендой и продлением, при сбое допускается повтор. Завершённые записи автоматически удаляются через 48 часов. Создание обращения `/paysupport` использует стабильный идентификатор источника и сохраняет одно обращение при повторе после сбоя отправки подтверждения. Платёжная защита по номеру платежа сохраняется; внешние отправки Telegram не входят в транзакцию MongoDB · 2026-10-23 · Никита
- **D5.** Создание счёта с тем же необязательным ключом повтора продолжает одну запись с прежними `invoicePayload` и снимком пакета, в том числе после сбоя получения ссылки. Ссылка защищена арендой с токеном владельца; истечение 24 часов освобождает только ключ запроса, финансовая история сохраняется. Идентификатор `pre_checkout_query` закрепляется до ответа Telegram; одобрение ещё не означает оплату. Хук `successful_payment`, сверка истории Stars и дозачисление `paid` используют одну функцию: условное изменение статуса и начисление ударов фиксируются одной MongoDB-транзакцией, без внешних запросов внутри неё. Обычный успешный переход — `invoiced → credited`; `paid` сохраняется для прежних записей и подтверждённых оплат, которые нельзя зачислить удалённому пользователю. Worker при запуске и раз в минуту сверяет ожидающие платежи старше пяти минут; отсутствие операции в истории оставляет ожидание. Несовпадающие подтверждения и найденные возвраты сохраняются в `PaymentIncident` для разбирательства, без повторного начисления и новых автоматических возвратов. Сверка работает отдельно от остальных заданий worker; её продолжение после рестарта начинается заново, само зачисление остаётся защищённым MongoDB · 2026-10-24 · Никита

## Контракт
Исторические допущения ручного контракта. При расхождении приоритет имеют D3–D10 и фактический экспорт Nest Swagger по D9.

Шаг contract, ветка `contract/mvp`. Статус допущений: не подтверждено, пока не сказано иное. Карта: [contract-map.md](contract-map.md).

### Допущения проектировщика контракта
- <a id="k1"></a>**К1.** Адреса действий над периодом — существительные в единственном числе: `POST /periods/{id}/completion|extension|surrender|retry`, ответ проверки — `PUT /feed/{id}/check-in-answer` (по сообщению, а не по периоду: бот и Mini App отвечают на конкретную проверку). Остановка задачи — `PATCH /tasks/{id}` со `status = stopped`. Маршруты из `modules.md` (`done`, `give-up`, `stop`, `replies`) заменены без смены смысла.
- <a id="k2"></a>**К2.** `Task` отдаёт вложенный текущий период (`currentPeriod` вместо `currentPeriodId`): исключение из правила «чужую модель не вкладывать» по комментарию каталога «чтение главной одним запросом», описано в схеме `TaskResponse`.
- <a id="k3"></a>**К3.** `DELETE /tasks/{id}` отвечает 200 с фразой onDelete, а не 204: ТЗ (R-35) требует показать фразу. Остальные удаления — 204.
- <a id="k4"></a>**К4.** Реплики персонажа в ответах действий — поле `reply` (готовый текст после подстановки, как `FeedMessage.text`; `null` — молчит). Ошибки с фразой (`task_vague`, `extension_denied`) несут её в расширении `Problem.reply`. Поле не из каталога сущностей: это составной ответ, не колонка.
- <a id="k5"></a>**К5.** Вычисляемые значения в ответах, которых нет в каталоге как колонки: `balance` и `strikesBalance` (сумма `remaining` партий), `rank` в рейтинге, метрики, отчёт наполнения. Клиент их не считает и не вводит.
- <a id="k6"></a>**К6.** Настроение задачи в API не отдаётся: клиент считает его из `moodFrom`, `anchorAt` и `deadline` по R-39 и R-46; уровень побеждённости 1–4 клиент считает из `defeat` по R-104.
- <a id="k7"></a>**К7.** Ход боя — `POST /battle/{role}/messages` с заголовком `Idempotency-Key` (он же `Turn.clientTurnId`), ответ 201 содержит итог хода и новые реплики. Ход, не засчитанный по ошибке, — 502 `turn_failed` (удар возвращён). «Ответить» — `POST /battle/{role}/quotes`.
- <a id="k8"></a>**К8.** Счёт Stars — `POST /packages/{id}/invoices`, ответ `invoiceUrl`; начисление Mini App узнаёт опросом `GET /me/strikes` до минуты. Подтверждение платежа идёт только через вебхук.
- <a id="k9"></a>**К9.** Идентификатор `id` есть у ресурсов, адресуемых по пути, даже если каталог его не перечисляет (Package, StarsPayment, SupportTicket, Phrase). У Turn, StrikeOperation, BattleMessage (используется `seq`), OwnerAction идентификатора нет.
- <a id="k10"></a>**К10.** Гость: `getMe`, `completeOnboarding`, `deleteMe`. Остальное пользовательское — 403 `onboarding_required`. Владелец проверяется по Telegram ID, чужой получает 403 `owner_only`. Ссылки на пользователя владельцу даются по Telegram ID, а не по внутреннему `id`.

### Вопросы архитектору и Никите
Контракт собран на предложенных вариантах и ждёт решения; ни один не блокирует сборку.

- <a id="кв1"></a>**КВ1.** Как клиент узнаёт, что пользователь — владелец (показать раздел «Владелец»). В каталоге признака нет. Варианты: 1) добавить в `User` вычисляемое `isOwner` (по Telegram ID из настройки) и отдавать в `MeResponse`; 2) клиент пробует `GET /owner/game-settings` и ловит 403. **Рекомендация:** 1.
- <a id="кв2"></a>**КВ2.** Тексты старта (`OnboardingResponse.replies`, в том числе «Снова начинаем» по `DeletedUser`) и `reply` во всех действиях собирает сервер. Подтвердить как составной ответ без новых полей сущностей (К4). **Рекомендация:** подтвердить.
- <a id="кв3"></a>**КВ3.** Нужна ли клиенту доступность кнопок «Продлить» и «Сделаю за час» заранее (`lastExtendedOn` и граница следующего периода скрыты по каталогу). Сейчас клиент показывает кнопку и получает 409 `extension_denied` / `retry_unavailable` с фразой отказа. Варианты: 1) оставить; 2) добавить вычисляемые `canExtend`, `canRetry` в `PeriodResponse`. **Рекомендация:** 1 для MVP (отказ — часть игры, R-33).
- <a id="кв4"></a>**КВ4.** Изменение уважения за «Готово», «Провал», «Сдаюсь» (экран «Уважение: 15 (+3)») — клиент считает как разницу новой и прежней `respect`. Подтвердить, что отдельное `respectDelta` вне боя не нужно. **Рекомендация:** подтвердить.
- <a id="кв5"></a>**КВ5.** Тип `OtherName.cases` в `GameSettings` (каталог пишет `cases`, тип не назван): принят список строк-форм по падежам. Уточнить формат склонений.
