# Единое расписание обращений по задачам

Статус: одобрено Никитой 2026-10-24. Решение заменяет независимые расписания и обязательные минимумы проверок каждой задачи (R-48–R-50, R-55), уточняет автоматические отправки R-57–R-63. REST DTO сохраняются. Настоящий ИИ, Redis и BullMQ сейчас не подключаются.

## Поведение

Персонаж один, расписание одно на пользователя. У него один следующий момент обращения и не больше одного ожидающего сообщения этого планировщика. Задачи, дедлайны, отсутствие активности, ответы и переносы дают контекст и поводы, без независимых рассылок.

Три минуты между успешно отправленными плановыми сообщениями — жёсткая нижняя граница, не период рассылки. Учитывается недавняя плотность. Рост числа задач усиливает давление с ограничением. Первые диапазоны: обычный 30–120 минут, застой 7–25 минут, короткая серия 3–10 минут, не больше двух дополнительных обращений серии, затем более длинная случайная пауза. Дополнительно ограничивается плотность за скользящий час. Конкретные защитные пороги выбираются при реализации и фиксируются в отчёте; публичный API настроек не расширяется.

Следующая дата выбирается один раз и сохраняется. Worker не перебрасывает её при каждом тике. Существенное событие (создание, закрытие, удаление, остановка, перенос, ответ, смена роли/тихих часов) делает план неактуальным. Обычные HTTP-чтения не сдвигают дату постоянно. Перед подготовкой и непосредственно перед отправкой проверяется актуальное состояние.

Основная задача выбирается по срочности, последнему ответу/переносу и давности упоминания. Другие задачи не должны постоянно вытесняться одной и той же. Иногда допускается короткое упоминание ещё одной задачи без списка. Кнопки и штраф за неответ относятся только к основной; вторичное упоминание не считается проверкой. Публичный `periodId` сохраняется. Тексты — шаблоны из пула, учитываются роль/пол, побеждённость и причина обращения. Новые действия для второй задачи и вызовы ИИ не добавляются.

Прежние фиксированные напоминания, провалы и отсутствие активности становятся поводами общего планировщика. Срочный повод может приблизить обращение, но не обходит общий интервал и ограничение плотности. Тихие часы, блокировка, отсутствие onboarding, удаление аккаунта и неактуальные задачи запрещают отправку. После простоя пересчитывается ситуация; старые поводы не догоняются пачкой. Нет подходящих задач или допустимых поводов — нет пустого сообщения.

Минимумы «две проверки каждой задачи в сутки» и «одна каждой короткой задаче» отменены. Вместо них — общее ограниченное давление, срочность и справедливый выбор. Отдельная отправка каждой задаче при перегрузке не обещается. Штраф за неответ не больше 3 уважения в сутки сохраняется; одна серия не штрафует многократно за один исходный неответ. Пятнадцать минут на ответ считаются от подтверждённой отправки, не от создания заготовки.

## Устройство

### Начальные параметры реализации

- Предел — 6 автоматических сообщений за скользящий час. Недавние неопределённые отправки также занимают осторожное окно плотности, но не считаются доставленными; явный отказ Telegram 4xx не считается принятой отправкой.
- Базовые диапазоны: обычный 30–120 минут, застой 7–25, серия 3–10, пауза 30–60. Серия — максимум два дополнительных обращения, срок жизни 90 минут. Побеждённость растягивает интервалы в 1 / 1,25 / 1,5 / 2 раза; число задач сокращает их максимум в 1,3 раза, усиление насыщается на четырёх задачах. Нижняя граница 3 минуты остаётся жёсткой.
- Срочность — срок или anchor ближе 120 минут; отсутствие активности — 6 часов; отрицательный ответ учитывается 6 часов, перенос — 24 часа. Повод провала актуален 24 часа и сообщается успешно один раз для конкретного провала; новый провал после retry — новый повод.
- Второе упоминание выбирается с вероятностью 25%, только активная задача. Основная задача явно названа. Давность основного упоминания учитывается отдельно от вторичного; ротация усиливается после 6 часов ожидания. Последнее основное упоминание берётся за всю историю активных кандидатов, без обрезания произвольными последними 200 сообщениями.
- Все параметры находятся в `apps/api/src/modules/task-notifications/task-notifications.policy.ts`. В дальнейшем их можно менять как политику, не меняя транспорт.

Модуль `task-notifications` владеет контекстом, частотой, выбором задачи, устойчивым следующим решением, сериями и фактами для будущего улучшения политики. Старый `pressure` может быть тонким адаптером; его независимое планирование отключается. `delivery` отвечает за техническую доставку, кнопки, сетевые повторы и подтверждение результата.

В MongoDB одно состояние на `userId`: следующая дата, ревизия/признак пересмотра, ограниченная аренда с токеном владельца, ссылка на единственное ожидающее сообщение, серия/пауза. Последнее успешное время отправки имеет один источник истины — можно сохранить `User.lastSentAt`. История успешных обращений сохраняет причину, основную/вторичную задачу и уровень давления; ответы и результаты связаны существующими идентификаторами. Не накапливать историю массивом в состоянии.

Существующий worker выбирает наступившие записи по индексу. Захват и завершение защищены условными Mongo-обновлениями, ревизией и токеном владельца. Внешняя отправка вне транзакции. После рестарта восстанавливается сохранённый план; истёкшая аренда доступна новому владельцу. Запоздалое сохранение старого плана не затирает новое событие. Успешная отправка устойчиво фиксирует факты и следующий план; отмена не засчитывает доставку и не запускает таймер неответа. Неопределённый исход Telegram сохраняет осторожную защиту интервала, без обещания абсолютно единственной внешней отправки.

Старые ожидающие сообщения независимого планировщика безопасно отменяются. При удалении аккаунта удаляются новое состояние и нефинансовая история. Предыдущие исправления платежей, ключей повторов, учёта Telegram updates и общего интервала сохраняются.
